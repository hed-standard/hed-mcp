# hed-mcp

Purpose: a Model Context Protocol (MCP) server that exposes HED (Hierarchical Event Descriptor) validation as MCP tools and resources, so an AI assistant or any MCP client can validate HED strings, BIDS JSON sidecars and BIDS TSV event files. The validation itself is done by the `hed-validator` npm package; this repo is the MCP wrapper, the schema cache, the issue formatting and the examples. Not in scope: the validator (hed-javascript), the HED schemas (hed-schemas), the browser validator app (hed-web).

## Commands

Test framework: jest (ts-jest, ESM; test files are `tests/**/*.test.ts`). Never convert the suite to another framework as a side effect of other work.

Run from the repo root, on Node.js 22 or later.

| Task | Command |
| --- | --- |
| Install | `npm ci` (from the lockfile; `npm install` changes it) |
| Build | `npm run build` (runs `prebuild`, which deletes `dist/`, then `tsc`) |
| Tests (the gate) | `npm run test:ci` (`npm test` is the interactive form) |
| One test file | `npx jest tests/tools/validateHedString.test.ts` |
| Coverage | `npm run test:coverage` (lcov and html under `coverage/`) |
| Spelling | `uvx typos --config .typos.toml` |
| Run, stdio transport | `node dist/src/server.js` |
| Run, HTTP API example | `npm run start:http` |
| Inspect interactively | `npx @modelcontextprotocol/inspector node dist/src/server.js` |

There is no linter or formatter; `ci.yml` runs `npm run lint --if-present` and nothing is present.

CI (`.github/workflows/`): `ci.yml` fails on any tracked file with CRLF line endings, then builds and runs `test:ci` on Node 22 and 24, checks that `dist/src/server.js` exists, and runs `npm audit` (allowed to fail); `typos.yaml` runs the spelling check; `coverage.yml` uploads coverage to qlty on pushes to `main`; `links.yaml` runs lychee weekly with `lychee.toml`; `release.yml` tests, builds and publishes on a `v*` tag. Dependabot opens weekly PRs for npm and GitHub Actions.

Never quote test counts or dependency versions in a committed file: they change with every dependabot merge.

## Layout

- `src/server.ts` - the server: registers the tools and resources, runs over stdio or WebSocket.
- `src/tools/` - one module per MCP tool: `validateHedString.ts`, `validateHedSidecar.ts`, `validateHedTsv.ts`, `getFileFromPath.ts`. Each exports the MCP tool definition, a zod schema built from it by `mcpToZod`, and an async `handle*` function.
- `src/resources/hedSchema.ts` - the MCP resource that describes a HED schema.
- `src/utils/` - `schemaCache.ts` (loads and caches schemas by version string), `definitionProcessor.ts` (definition strings to a `DefinitionManager`), `issueFormatter.ts` (validator issues to the MCP response shape), `fileReader.ts`, `mcpToZod.ts`.
- `src/types/index.ts` - the shared result types.
- `tests/` - mirrors `src/`; fixtures in `tests/data/` (BIDS TSV and JSON files, including deliberately bad ones).
- `examples/` - an HTTP server, an MCP client, and browser clients; compiled into `dist/examples/` with the source.
- `dist/` - generated by the build and gitignored; `dist/src/server.js` is the entry point. `coverage/` likewise.
- `mcp-config.json` - a client configuration to copy; its `cwd` is a placeholder.
- `API.md`, `EXAMPLES.md`, `CHANGELOG.md` - the tool reference, worked examples, and release history.
- `.status/` - working notes. Gitignored; local to each machine.

## Conventions that differ from defaults

- **ASCII only** in prose, code, comments, and filenames: `-` not em or en dashes, `->` not arrows, `...` not an ellipsis character, straight quotes, `|--` not box-drawing characters in tree diagrams. Exception: genuine data (author names, dataset titles, recorded responses) keeps whatever characters it actually contains.
- Markdown headers are sentence case.
- Two-space indentation in TypeScript, as the files are; there is no formatter to enforce it.
- Line endings are LF; `.gitattributes`, `.editorconfig` and the CI check enforce it.
- Committed files carry no project history and no local paths or drive letters.

## Rules that are easy to get wrong

- `hed-validator` is pinned to an npm release, never to a git commit: this package publishes a `bin`, and a git dependency would make every consumer build the validator from source at install time.
- Schema versions bundled in `hed-validator` (such as `8.4.0`) load offline; any other version is fetched from GitHub by the validator, so a test that uses one needs the network.
- `tsconfig.json` compiles `src/` and `examples/` with `rootDir` at the repo root, which is why the build lands in `dist/src/` and `dist/examples/`, not `dist/`. `tests/` compile separately under `tsconfig.test.json` (CommonJS).
- `jest.config.mjs` maps `hed-validator` to its CommonJS build by path; a package layout change in hed-validator breaks the suite there first.
- The fork this repo is developed from is named `hed-mcp-typescript`; the repository and the package are `hed-mcp`.

## Where the thinking lives

`.status/` is gitignored, so it exists only on the machine that wrote it and never in a fresh clone or worktree.

- `.status/README.md` - current state, unfinished work, and an ordered `Next` list. Read this first.
- `.status/development_history.md` - what has shipped, newest first, with pointers to the records. History only; append at the top when a PR merges.
- `.status/decisions.md` - why things are the way they are. Read before proposing structural changes. Append entries; never rewrite one.
- `.status/plans/*.md` - unfinished plans only. Check the `Status:` header and the `[ ]` / `[x]` markers before starting work. A finished plan moves to `.status/archive/completed_plans/`, renamed `archived_YYYY-MM-DD_<name>` with the day it was archived; split any still-open boxes into a new plan first.
- `.status/notes/` - dated records, always named `YYYY-MM-DD_<slug>.md`. Write-once.
- `.status/local-environment.md` - this machine's paths, interpreter, and quirks. Tool-agnostic. Never copy its contents into a committed file.
- IMPORTANT: do not read `.status/archive/` unless a file is named for you. The `.status/` root holds only `README.md`, `decisions.md`, `development_history.md`, and `local-environment.md`; nothing else is created there.

## Working agreements

- IMPORTANT: every file written to `.status/` opens with a `For humans:` summary - three or four sentences, at the very top: what the file is and what a person needs to take from it. The same applies to a long answer in a session: lead with the conclusion.
- IMPORTANT: temporary scripts, experiments, and one-off test files go in `.status/scratch/` - **never the repository root**. Anything in `scratch/` may be deleted unread.
- IMPORTANT: never delete or rewrite a file under `.status/` without asking first. Appending is fine.
- For a change spanning more than three files, write a plan to `.status/plans/` and stop for review before editing.
- When you are guessing about an external API or data format, say so explicitly rather than assuming.
- Show evidence, not assertions: the command you ran and its actual output.
- Do not commit, push, or create branches unless asked.
